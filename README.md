# DTM工程管理

楽曲制作(DTM)の作業を「セクションごとのタスク」として管理するローカルWebアプリ。1曲を1プロジェクトとし、複数のプロジェクトを並行して持てる。

- 構成(セクション)は自由に編集できる。歌モノ以外にも使える。
- 「毎回やる定番作業(ノウハウ)」をライブラリに持ち、プロジェクトを作るたびにコピーする。ノウハウは使うほど育つ。
- 運用ルールに頼らず、型はツール側の構造で保つ。
- 計画変更(セクションの追加・削除・並べ替え、タスクの移動)を気軽にできる。

## 現在の状態

## 起動

ビルドは不要。静的サーバーで配信して開く(`file://` では ES Modules が動かない)。

```
python -m http.server 8765      # または npx serve .
```

`http://localhost:8765/` を開くとログイン画面が出る。Supabase の Project URL と公開キーを入れるか、「ログインせずに使う」を選ぶ(その場合、データはそのブラウザの IndexedDB に入る)。

テストは `http://localhost:8765/test.html` を開くか、Node で実行する。

```
node -e "import('./test/domain.test.js').then(m => m.report()).then(ok => process.exit(ok ? 0 : 1))"
```

## 保存先とログイン

- **擬似ログイン**:ログイン画面で Supabase の Project URL と公開キー(anon / publishable key)を入力する。接続を確かめてから、入力値をそのブラウザの localStorage に保存する(`js/session.js`)。Supabase Auth によるユーザー認証はしていない。
- **1つの Supabase プロジェクトを1人で使う前提**。Project URL と公開キーを知っていれば全データを読み書きできる。だから公開キーはリポジトリに入れず、人にも渡さない。
- **テーブルの用意**:`supabase/schema.sql` を Supabase の SQL Editor に貼り付けて実行する(初回だけ。何度実行してもよい)。
- **ログインせずに使う**こともできる。その場合の保存先はそのブラウザの IndexedDB。Supabase 側とは別のデータで、自動では移らない(移すには、エクスポートしてからログイン後にインポートする)。
- **当面の運用**:機能追加が落ち着くまでは、ログインせずに(IndexedDB で)使う。項目を足しても移行作業が要らず、操作も速いため。データは「そのブラウザの、そのURL(ポート番号を含む)」にしかないので、同じブラウザ・同じポートで開き、区切りごとに JSON をエクスポートしてバックアップを取る。固まったら Supabase に移行する(手順は「これから」を参照)。
- **ログアウト**は設定画面から。localStorage の接続情報を消すだけで、Supabase 上のデータは残る。
- Supabase に保存しているときは、操作のたびに通信する(読む→保存→読み直す)。オフラインでは使えない。

## 仕様

### 決めたこと

| 項目 | 決定 |
|---|---|
| 工程軸(作曲→編曲→ミックス…) | 持たない。マトリクス表示もしない |
| 動線(作業順) | レーン内の並び順で表現する。初期順は定番タスクの登録順で、以後はドラッグで入れ替える。タスク間の依存関係は持たない |
| 定番作業の単位 | セクション種別ごとの定番と、「全体」の定番の2系統 |
| タスクの属性 | タイトル / ステータス(未着手・作業中・完了) / メモ。見積もり時間は持たない |
| 締切 | プロジェクトごとに任意で1つ(日付のみ)。一覧のカードとボードに残り日数を出す。3日以内は強調、過ぎたら超過日数を赤で出す。全タスク完了なら日付だけ |
| 定番の適用 | コピー方式。作成時に複製するので、ライブラリを後から編集しても作成済みのプロジェクトには影響しない |
| 「全体」レーン | すべてのプロジェクトに必ず1本ある。構成テンプレートには含めない。名前変更・複製・削除・並べ替えはできない |
| 色 | 選ばせない。プロジェクトごとに、セクションの並び順で固定パレットの色を先頭から割り振る(同じ種別のセクションは同じ色)。パレットは18色で、系統の違う9色(Tailwind の500)と、それぞれを明るくした9色(同300) |
| タスクの出自 | 持たない。定番からコピーしたタスクも、プロジェクトで足したタスクも区別しない(名前を変えると区別の意味がなくなるため) |
| 定番への追加先 | タスクが所属するレーンで決まる。セクションのタスクはその種別の定番、「全体」レーンのタスクは「全体」の定番 |

### 画面

| ルート | 画面 | 内容 |
|---|---|---|
| `#/` | プロジェクト一覧 | カード(進捗、締切、最終更新)。新規作成はタイトルと構成テンプレートを選ぶだけ |
| `#/p/:id` | ボード | 「全体」レーンを左端に固定し、セクションのレーンを横に並べる。上部にセクション一覧(チップ)があり、構成を俯瞰でき、押すとそのレーンへジャンプする。スマホではレーンを縦に積む |
| `#/library` | ライブラリ | セクション種別、種別ごと・「全体」の定番タスク、構成テンプレート |
| `#/settings` | 設定 | 保存先の表示とログアウト、JSONのエクスポート/インポート |

ボードでできること:

- ステータス切替(丸をクリックで 未着手 → 作業中 → 完了 と循環。保存を待っている間は丸が回る)、レーン末尾のクイック入力(Enterで連続追加)
- タスクのドラッグ(レーン内の並べ替え、レーン間の移動)、セクションのドラッグ(ヘッダーを掴む)
- セクションの追加(レーン間の「+」または末尾のボタン。種別の定番タスクつき、または空で)、名前変更、複製、折りたたみ、削除
- タスク詳細(PCは右ドロワー、スマホはボトムシート)で編集・削除・定番への追加
- 「未完了のみ」フィルタ
- レーン・タスク・定番タスクの削除は、トーストから直前の1回を元に戻せる

### 知っておく挙動

- **セクションの色**は保存していない。表示のたびに、並び順の先頭から種別ごとにパレットの色を割り振る。だからセクションを並べ替えると色も入れ替わる(赤のAメロ・青のBメロを入れ替えると、Bメロが赤、Aメロが青になる)。種別のないセクションは名前(末尾の番号を除く)で見分ける。19種類目からはパレットの先頭に戻る。
- **定番に追加**すると、タイトルとメモをライブラリにコピーする。タスク自体は変わらない。同じタイトルの定番がすでにあれば追加しない。種別のないセクションのタスクは追加できない。
- **「プロジェクト」タブ**は、閲覧中のプロジェクトがあればそのボードに戻る(ライブラリや設定を見たあとで戻れる)。プロジェクト一覧へは、左上のタイトルかボードの「←」で行く。一覧を開くと「閲覧中」は解除される。
- **ライブラリ**は、ページ全体ではなく2カラムの領域(`.library-cols`)がスクロールする。項目数でスクロールバーが出入りしても画面幅が変わらないようにするため。
- **セクション種別を削除**すると、その定番タスクも消え、構成テンプレートからも外れる。作成済みプロジェクトのセクションは残る。
- **インポート**は既存データをすべて置き換える(マージしない)。Supabase では1つのトランザクションではないので、途中で失敗したら同じファイルをもう一度インポートする。
- **初期データ**の構成テンプレートは「歌モノ」と「インスト」の2つ。
- **初期データ**が入るのは、保存先ごとに最初の1回だけ。入れ直す機能はない(消した初期データを戻したいときは、ライブラリで作り直す)。

## 技術方針

- 素の HTML / CSS / JavaScript(ES Modules)。ビルドステップなし。そのまま GitHub Pages に置ける。
- 外部依存は CDN から読む2つだけ。**SortableJS**(ドラッグ&ドロップ)と **Lucide**(アイコン)。
- 保存先は Supabase(REST API を `fetch` で直接呼ぶ。SDK は使わない)か、IndexedDB。保存処理は repository 層で抽象化してあり、UIとドメインロジックはどちらに保存しているかを知らない。
- ルーティングはハッシュ方式。
- IDは `crypto.randomUUID()`(初期データだけは固定ID)。
- 並び順は小数の `order`(fractional indexing)。間に入れるときは前後の中間値を使い、他の行を書き換えない。精度が尽きたときだけ全体を振り直す。
- 全レコードに `createdAt` と `updatedAt`。エクスポートデータには `schemaVersion`(現在 2)。古いデータは、インポートのときに `migrate` が廃止した項目を落とす。

### データの流れ

1. 画面が `actions.js` の操作を呼ぶ。
2. 操作は repository から読み、`domain/` の関数で保存すべきレコードを計算し、保存して `notify()` する。
3. 各画面は `subscribe()` で通知を受け、repository から読み直して全体を再描画する。フォーカスと入力中の値は `data-focus-key` を目印に引き継ぐ(`keepFocus`)。

操作は1つずつ順番に実行される(`serial`)。並行して走ると、後から保存した方が先の変更を消してしまうため。

### データモデル

```js
Project  { id, title, memo, dueDate }      // dueDate は 'YYYY-MM-DD' または null
Lane     { id, projectId, type: 'section' | 'global', name, kindId, order, collapsed }
Task     { id, projectId, laneId, title, memo, status: 'todo' | 'doing' | 'done', order, doneAt }

SectionKind       { id, name, order }
TemplateTask      { id, scope: 'kind' | 'global', kindId, title, memo, order }
StructureTemplate { id, name, sections: [kindId, ...], order }
```

すべてに `createdAt` と `updatedAt` が付く。`Lane.type === 'global'` が「全体」レーン。詳しい型は `js/store/repository.js` にある。

## これから(未着手)

- **「次やる」ビュー**:各レーンの未完了タスクの先頭と作業中のタスクを横断して一覧にする。使ってみて欲しくなったら追加する。
- **Supabase への移行**(機能が固まったら行う):
   1. `js/store/supabase.js` を、テーブルにある列だけを送るように直す(コレクションごとの列の一覧を持ち、`toRow` でそれ以外の項目を落とす)。いまはレコードの項目をそのまま列として送るので、ローカル運用中に「足してから消した項目」がレコードに残っていると、インポートがその列で失敗する。`test/domain.test.js` に、余分な項目を持つレコードを保存・インポートしても失敗しないことのテストを足す。
   2. その時点の `supabase/schema.sql` を SQL Editor でもう一度実行する(廃止した列はここで落ちる。足した列があれば、テーブルを作り直すか列を追加する)。
   3. ローカルで JSON をエクスポート → ログイン → インポート。インポートは Supabase 上の既存データをすべて置き換える。
- **GitHub Pages でのホスト**:GitHub にリポジトリを作って push し、Settings → Pages で `main` ブランチのルートを公開する。ビルドは不要。
- **速度と通信の改善**:Supabase では1操作あたりの通信回数が多い。読み直しを減らす(手元の状態を先に更新する)、オフライン時に書き込みをキューに貯めて再送する、など。
- **本物の認証**:複数人で使う、または公開キーを秘密にしたくない場合は、Supabase Auth と user_id 単位の RLS に切り替える。
- **工程タグ**:必要になったら、タスクに任意のタグを付けてフィルタできるようにする。

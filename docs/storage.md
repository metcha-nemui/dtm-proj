# 保存・ログイン・PWA

## 保存先とログイン

- **擬似ログイン**:ログイン画面で Supabase の Project URL と公開キー(anon / publishable key)を入力する。接続を確かめてから、入力値をそのブラウザの localStorage に保存する(`js/session.js`)。Supabase Auth によるユーザー認証はしていない。
- **1つの Supabase プロジェクトを1人で使う前提**。Project URL と公開キーを知っていれば全データを読み書きできる。だから公開キーはリポジトリに入れず、人にも渡さない。
- **テーブルの用意**:`supabase/schema.sql` を Supabase の SQL Editor に貼り付けて実行する(初回だけ。何度実行してもよい)。テーブルは、レコードを jsonb のまま入れる `records` と、`app_meta` の2つだけ。アプリ側で項目を足したり変えたりしても、実行し直す必要はない。空の状態から作り直したいときは、先に `supabase/drop.sql` を実行する(データはすべて消える)。
- **ログインせずに使う**こともできる。その場合の保存先はそのブラウザの IndexedDB。Supabase 側とは別のデータで、自動では移らない(移すには、エクスポートしてからログイン後にインポートする)。
- **使い分け**:実際の作業の記録は Supabase に置く。Supabase の実データに触らずに試したいとき(画面の動作確認など)は、ログインせずに(IndexedDB で)使う。IndexedDB のデータは「そのブラウザの、そのURL(ポート番号を含む)」にしかない。
- **ログアウト**は設定画面から。localStorage の接続情報を消すだけで、Supabase 上のデータは残る。
- Supabase に保存しているときは、操作のたびに通信する(読む→保存→読み直す)。オフラインでは使えない(IndexedDB ならオフラインでも使える)。
- **通信に時間が掛かったとき**:操作(`actions.js` の各操作とインポート)が5秒を過ぎても終わらなければ、画面下に「処理中です…」を出し、終わるまで出し続ける(いくつも待っていれば、すべて終わるまで)。3秒以上かかって正常に終わったら「保存が完了しました」のトーストを出す(続けて「元に戻す」などのトーストが出る操作では、そちらに置き換わる)。時間は操作を呼んだときから測る(前の操作の終わりを待っている間も含む)。失敗したときはエラーのトーストだけを出す。保存先が IndexedDB でも同じ(ふつうは速いので出ない)。`js/ui/components/slowNotice.js`
- **Supabase に届かないとき**:操作はすべて失敗し、そのたびにトーストで知らせる(「読み込みも保存もできませんでした」)。成功したように見せたまま捨てることはしない。
   - 端末がオフラインの間は、画面の上端に「オフラインです…変更は保存されません」のお知らせを出し続ける(`js/ui/connectionBanner.js`)。オンラインに戻るとお知らせを消し、保存先から読み直して描き直す。
   - 画面を先に動かすドラッグ(ボードのタスク・セクション、アレンジ)は、保存に失敗したら保存済みの並びに描き直す。
   - タスク詳細の入力は、保存に失敗しても欄に打った内容を残し、次に欄を離れたときや閉じるときに保存し直す(閉じるときにも失敗すると、その内容は残らない)。
   - 起動時に届かなければ、「データを読み込めませんでした」と再試行のボタンを出す。
   - オフラインの間の変更を貯めておいて後で送る仕組みはない(README の「これから」を参照)。

## データの扱い

- **インポート**は既存データをすべて置き換える(マージしない)。Supabase では、先にファイルの中身を上書きで入れてから、ファイルにない行を消す。1つのトランザクションではないので、途中で失敗したら同じファイルをもう一度インポートする(失敗しても、行が消えすぎることはない)。
- **削除の連鎖**(プロジェクト → レーン・タスク・アレンジ、レーン → タスク・マーカー、トラック → クリップ)は、アプリ側で行う(データベースの外部キーには頼らない)。子を先に消し、親を最後に消すので、途中で失敗しても、もう一度消せば揃う。
- **端末ごとのファイル**:音源(SoundFont / DLS)とオーディオトラックの音声ファイルは、保存先(Supabase / IndexedDB)とは別の、そのブラウザの IndexedDB に入れる。エクスポートにも含めない。オーディオトラックが持つのはファイルの id と名前・サイズ・長さだけで、中身のない端末では画面で選び直す([arrangement.md](arrangement.md) の「オーディオトラック」)。ログインせずに使うときと Supabase のときで、音声ファイルの置き場所は共通(プロジェクトの id で見分ける)。
- **初期データ**はない。初めて使う保存先は空で始まる。
- **古いデータ**:`schemaVersion` 3 以下のデータ(IndexedDB もエクスポートJSONも)は読み込めない(開いたときに消えて空から始まる)。4 以降は `migrate` で変換して読み込む。どの版で何を補うかは `js/store/repository.js` の `SCHEMA_VERSION` の上のコメントにある。

## スキーマバージョン

- 全レコードに `createdAt` と `updatedAt`。エクスポートデータと保存先の meta に `schemaVersion`(値は `js/store/repository.js` の `SCHEMA_VERSION`)。
- 保存先の記録がなければ 6 とみなす。ただし、以前の初期データを入れた印(meta の `seeded`)もない、初めて使う保存先は、変換せずに現在のバージョンを記録する。起動時に `upgradeStorage` がアプリのバージョンと比べる。
   - 保存先が古い:変換前の全データを meta の `backup:v{旧バージョン}:{日時}` に残してから、`migrate` で変換して保存し直し、バージョンを上げる。途中で失敗したらバージョンは上がらないので、次の起動でやり直される。
   - 保存先が新しい(別の端末やタブで新しいアプリが変換した):古い形で書き込むと壊れるので、「再読み込みしてください」を出して止める。開いたままのタブに戻ってきたとき(`visibilitychange`)にも確かめる。
   - スキーマを変えるときは、`SCHEMA_VERSION` を上げ、`migrate` に変換を足し、上のコメントに1行足す。Supabase のテーブルは変えない。
- 項目を足すだけで、なければ既定値として扱えるもの(タスクの `startDate` / `endDate` / `references`、Track の `mute` / `solo`)は、バージョンを上げていない。
- IndexedDB のデータベースのバージョンは 4(ストアの構成を変えないかぎり、スキーマを変えても上げなくてよい)。

## 保存先の実装

- 保存先ごとの実装は「文書ストア」(`DocumentStore`:レコードを JSON のまま、コレクション単位で読む・書く・1項目の一致で絞って消す)だけを持つ。repository の各メソッド、削除の連鎖、エクスポート/インポート、スキーマの変換は、その上に `js/store/repository.js` の `createRepository` で1回だけ組み立てる。
- Supabase は REST API を `fetch` で直接呼ぶ(SDK は使わない)。全レコードを1つのテーブル(`records`)に入れ、項目は `data` 列(jsonb)にそのまま持つ。列に出すのはコレクション名・id・プロジェクトの id だけ。レーンやトラックでの絞り込みは `data->>laneId` のように jsonb の項目で行う。
- 以前の、項目ごとに列を持つテーブルから乗り換えるとき:JSON をエクスポート → SQL Editor で `supabase/drop.sql`、続けて `supabase/schema.sql` を実行 → ログイン → インポート。

## PWA

Chrome / Edge ならアドレスバーのインストールボタン、スマホならメニューの「ホーム画面に追加」で、アプリとして独立したウィンドウで開ける。

- 一度開くと、画面のファイル(HTML・CSS・JS と CDN のライブラリ)が Service Worker(`sw.js`。登録は `js/pwa.js`)にキャッシュされ、オフラインでも起動できる。
- オフラインで使えるのは、ログインせずに(IndexedDB で)使っているときだけ。Supabase に保存しているときは、起動はできても読み書きできない。
- 同じオリジンのファイルはネットワーク優先、CDN のファイル(URL にバージョンが入っている)はキャッシュ優先で返し、Supabase への通信には関わらない。つながっていれば常に最新が使われるので、ファイルを変えたときにキャッシュの名前を変える必要はない。
- 最初に開いたときの読み込みは Service Worker を通らないので、登録後に画面が読み込み済みのファイルの URL を渡してキャッシュさせる(初回からオフラインで開けるように)。
- キャッシュ(Cache Storage)が使えないとき(壊れている、容量の上限など)も、ネットワークから取れるものはそのまま返す。キャッシュの失敗で画面が開けなくなると、Service Worker を消すまで直らないため。
- Service Worker は `localhost` か HTTPS でしか動かない(GitHub Pages は HTTPS なので動く)。パスはすべて相対にしてあるので、GitHub Pages のサブパスでも動く。
